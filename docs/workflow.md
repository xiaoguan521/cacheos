# 开发工作流

六个互相独立的步骤，可以从任意一步进入、跳过已有的前置产物。拿到别人给的规格，直接从第 3 步开始即可。目的是把关键判断留在人手里，不是填表。

| 步 | 做什么 | 产出 | 完成标准 | 对应技能 |
|---|---|---|---|---|
| 1 | 暴露风险与决策 | 风险清单（每条一行：风险、影响、处置） | 决策树每个分支走完，没有悄悄假设；你确认 | `grilling` / `grill-with-docs` |
| 2 | 整理确认的内容 | 规格文档 | 只含问题、方案、用户故事、实现决策、测试决策、范围之外；**不含代码和文件路径** | `to-spec` |
| 3 | 拆任务 | 任务清单 | 每个任务贯穿所需各层、能单独验证、一个 PR 可合并；标明依赖与前后端分项验收 | `to-tickets` |
| 4 | TDD 实现 | 红 → 绿的提交 | 先有失败用例；测试只放在事先确认的接缝；不写推测性功能 | `tdd` |
| 5 | 深模块 | 评审结论 | 新增模块通过删除测试；没有只转发的浅模块 | `codebase-design` |
| 6 | 大扫除 | HTML 报告，挑一项重构 | 报告只读，改动走第 1 步重新追问 | `improve-codebase-architecture` |

## 约定

- **风险清单**固定要过的项：许可、ACL 与拒绝清单、协议与升级兼容、数据面改名边界、升级与回滚、审计与密钥。
- **规格**与 ADR 的分工：规格说“做什么、怎么验收”，ADR 记录“难以回头且有取舍的决定”。两者都不放代码。
- **任务**写在 `.scratch/<功能>/issues/<序号>-<名称>.md`（不进仓库）；格式见 `to-tickets` 的本地模板，并加前端、后端、agent、协议四项分项验收。
- **术语**以 `GLOSSARY.md` 为准；新词在追问中确定后立即补进去。
- 这些技能都只能手动调用；追问和大扫除不会自动开始。

## 现有测试入口

| 范围 | 命令 |
|---|---|
| Go（控制台、agent、webcli 等） | `go test ./... && go vet ./...` |
| 数据面门禁 | `make ci`（patch、品牌、构建、版本、黄金验收、互通、客户端矩阵） |
| 模块清单与许可脚本 | `make modules-check` |
| 前端静态检查与类型 | `pnpm -C web run lint`、`pnpm -C web run build` |
| 前端行为 | `web/e2e/ui-acceptance.cjs`（Playwright 端到端冒烟） |

已知缺口：前端没有单元测试框架，只有端到端冒烟；`web/src/utils` 里的纯逻辑（如命令行参数解析）没有测试。
